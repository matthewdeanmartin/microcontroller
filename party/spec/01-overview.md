# 01 — Overview

## What it's for

| Audience | Where they are | How they use party |
|---|---|---|
| The house | On the home Wi-Fi | Full local app at `http://party.local`: everything, live |
| Family in other houses | Their own homes | Companion site (read via their personal link), RSVP by Mastodon DM, email notifications. Full app when they visit |
| Email-only people | Anywhere | Email invitations, updates and reminders with calendar attachments; a link that shows the event. Answers go through someone in the house, or the app on a visit (or the optional relay) |
| The open internet (stretch) | Anywhere | Public groups on the companion site, join and RSVP by DM, after invitation. Open registration is [roadmap](roadmap.md) |

## Non-goals

Carried from the draft: no forums, no feeds generated by party, no
recommendation algorithm, no payments or ticketing, no real-time chat, no
ActivityPub. Plus:

- **No inbound internet connections to the board, ever.**
- **No required paid service.** GitHub Pages, a mastodon.social account and
  Brevo's free plan are the baseline. Cloudflare is optional ([08](08-relay.md)).
- **No dependence on an LLM.** It's an optional translator in front of the DSL.

## Architecture

```
                   home LAN                       │            internet
                                                  │
  phones/laptops ── http(s)://party.local ──┐     │
                                            ▼     │
                                     ┌──────────┐ │ outbound HTTPS only
                                     │  ESP32-S3│─┼──► mastodon.social   (bot: poll mentions, send DMs)
                                     │  party   │─┼──► api.github.com    (publish snapshot to data repo)
                                     │          │─┼──► api.brevo.com     (send email)
                                     │          │─┼──► openrouter.ai     (optional: free text → DSL)
                                     └──────────┘─┼──► relay (optional Cloudflare Worker, polled)
                                                  │
                                                  │   GitHub Pages: companion site + published data
                                                  │        ▲ read                ▲ read
                                                  │   family/public browsers ── DM to bot via the
                                                  │                           person's own Mastodon
```

The board is the only writer of canonical state. Everything outside the house
is either a **snapshot** it published or a **message** waiting in a queue it
polls. Nothing outside can reach it, so nothing outside can overload it.

### Components

| Component | Runs on | Job |
|---|---|---|
| REST API + local app | board | Canonical CRUD, auth, rules. Serves the Angular app |
| Service layer | board | One set of commands (`rsvp`, `join`, `create_event` …) and one permission check, used by REST, DM, email and relay inputs alike |
| Inbox worker | board | Poll Mastodon mentions (and the relay, if configured), dedupe, parse, execute, queue replies |
| Outbound worker | board | DMs, email, publication, OAuth network steps. One at a time, bounded queue, backoff |
| Publisher | board | Build public + sealed snapshots, push changed files to the data repo |
| Companion site | GitHub Pages | Static Angular app. Reads published data, decrypts what the viewer's keys open, sends DMs through the viewer's Mastodon account |
| Demo site | GitHub Pages | Same app with bundled fictional data and a simulated bot |
| Relay | Cloudflare (optional) | A mailbox the companion site can drop signed commands into, and the board polls |

The workers share the board with the web server cooperatively: network steps
happen off the request path, and no request waits on the internet.

## Risk model

- **The house LAN is trusted the way Game Matcher trusts it:** household, kids,
  guests with the Wi-Fi password. PIN sign-in works only on the LAN, because the
  board is only reachable there.
- **GitHub Pages is world-readable, including git history.** Only data classed
  `public` is published as plaintext ([05](05-companion-site.md#data-classes)).
- **Mastodon DMs are not end-to-end encrypted.** Instance admins on both ends
  can read them. They carry commands, short confirmations and personal links,
  never PINs or member lists.
- **Personal links are bearer credentials.** Whoever holds one can read what it
  decrypts (and, with the relay, answer as that person). They can be reset.
- **The board's flash is not encrypted.** Bot token, GitHub token, Brevo key
  and keys for sealing are readable by anyone with the board and a USB cable.
  Same as the other household boards. Flash encryption is roadmap.

## Hardware

**Target: ESP32-S3 N16R8** (16 MiB flash, 8 MiB octal PSRAM), framework
`BoardConfig::s3()`. The household already runs mastomini, the bots and
NanaCoin on this board, so its TLS, PSRAM and storage behaviour is known.

- The S2 is ruled out (owner decision). The C6 has no PSRAM and Game Matcher
  already fills 92% of its app space.
- The P4 is fine to support later but must never be required.
- PSRAM holds the in-RAM indexes, the outbound queue and snapshot build
  buffers. Internal RAM stays for TLS and the connection loop.
- Sprint 0 measures the parts that are new for this app: many-record NVS boot
  time and concurrent outbound TLS while serving ([sprints](sprints.md#sprint-0-skeleton-and-the-s3-gate)).

Which physical S3 board party gets is an [open question](open-questions.md).

### Flash layout (proposed, 16 MiB)

| Partition | Size | Notes |
|---|---|---|
| nvs | 24 KiB | framework settings, Wi-Fi |
| otadata | 8 KiB | reserved for OTA |
| app0 | 4 MiB | firmware + gzipped local app |
| app1 | 4 MiB | reserved for OTA (empty until [OTA](roadmap.md#ota)) |
| partydata | 7.5 MiB | NVS partition: the record store ([07](07-storage-limits.md)) |
| coredump | 64 KiB | |

Reserving app1 now avoids a later partition change, which would mean an
export/import that doesn't exist yet.
